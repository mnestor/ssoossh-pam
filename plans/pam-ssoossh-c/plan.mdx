# pam_ssoossh in C

`pam_ssoossh.so` authenticates a local account by asking `ssoosshd` for a
short-lived SSH certificate, showing the approver a URL, waiting for a human to
approve it in a browser, and then validating the certificate that comes back.
Today that module is Go compiled with `-buildmode=c-shared`, and the artifact is
**12,890,192 bytes** that gets `dlopen`ed into `sudo` and `sshd`.

This plan rebuilds it in C11 against `libpam`, `libcurl`, and `libcrypto`, in a
standalone repository at `~/git/ssoossh-pam-c`, with byte-for-byte parity on the
wire protocol and the authentication decision. **Done** means: the C module
passes a differential test against the Go module across the full scenario matrix,
survives fuzzing of every parser that touches network bytes, and authenticates a
real `sudo` against a real `ssoosshd` on glibc and musl.

<Callout id="why-not-just-size" tone="decision">

**Size is the visible reason; the process boundary is the real one.** A Go
`c-shared` object initializes the Go runtime on load — it starts its own OS
threads, installs signal handlers into the host process, and cannot be
`dlclose`d. PAM modules are loaded and unloaded by a host that owns its own
threads and signal dispositions. The current module additionally calls
`signal.NotifyContext(os.Interrupt, syscall.SIGTERM)` on every authentication,
taking over `sudo`'s SIGINT for the duration of the call. C removes that whole
class of interaction, and the 85× size reduction comes along with it.

</Callout>

## Scope

**In scope.** The `auth` stack only: `pam_sm_authenticate` and
`pam_sm_setcred`, matching what exists today. All seven module arguments, the
`ssoosshd` HTTP + SSE protocol, ECDSA P-384 ephemeral key generation, SSH
certificate parsing and signature verification, the four validation checks, the
principals-map subset parser, syslog output, and the `PAM_TEXT_INFO`
conversation. Three PAM implementations: Linux-PAM on glibc and on musl
(x86-64, arm64), and OpenPAM on FreeBSD and macOS.

**Out of scope.** No `account`, `session`, or `password` stack — the module
implements none today and adding one changes what a `pam.d` file may contain.
Through P6, no new module arguments, no new endpoints, and no protocol changes:
this module speaks the same wire protocol as the Go one, and a deployment can
run either against the same server. Windows is not a target.

**Console mode is scoped but not sequenced with the port.** The module half of
`docs/proposals/console-login-pam.md` is designed here and lands as P7, on
Linux and FreeBSD only. Its server, schema, and frontend halves stay in the Go
monorepo and have to ship first — see Console mode below.

One argument is dropped rather than ported: `debug=stdout`. Writing to stdout
from inside `sudo` violates the module's own rule about the host owning that
stream, and the value exists only as a developer convenience. `debug=stdout`
stays *accepted* — it is treated as plain `debug` and logs to syslog — so no
existing `pam.d` line fails to parse.

## The contract to preserve

Three surfaces are observable from outside the module and must not drift: the
module arguments an operator writes in `pam.d`, the return code the PAM stack
branches on, and the four checks that decide the answer.

### Module arguments

Parsed the same way: split each `argv` element on its **first** `=`, so values
may contain `=`; an element with no `=` is the boolean `true`; an empty key is
skipped. libpam has already resolved `key=[bracketed value]` before the module
runs, so bracketed spaces need no handling here.

<Callout id="duration-parsing" tone="risk">

`skew-tolerance` and `timeout` are parsed by Go's `time.ParseDuration` today,
which accepts `1h30m`, `500ms`, `2s`, `1.5h`, and signed values. C has no
equivalent in libc, so `duration_parse()` is a real (small) porting task, not a
call to `strtol`. An existing `pam.d` line using `timeout=2m` must keep working.

</Callout>

### Return codes

The Go module hardcodes numeric PAM constants in `return_values.go` rather than
reading them from the headers. Those numbers match Linux-PAM exactly — verified
against `/usr/include/security/_pam_types.h` on this machine — so the current
module is correct on Linux and silently wrong on OpenPAM, where the numbering
diverges: `7` is `PAM_PERM_DENIED` there, not `PAM_AUTH_ERR`. With FreeBSD and
macOS in scope, taking the constants from `<security/pam_modules.h>` stops being
hygiene and becomes the thing that makes those targets possible at all.

`PAM_AUTHINFO_UNAVAIL` for an unreachable server is deliberate and worth
keeping: it lets the stack fall through to whatever follows in `/etc/pam.d`, so
an ssoossh outage does not become a `sudo` outage on every host. A server that
answered and said no is `PAM_AUTH_ERR`.

`PAM_IGNORE` on Ctrl-C is new — the Go module returns `PAM_AUTH_ERR` there,
which tears down the whole `sudo` attempt. `PAM_IGNORE` means "this module
contributes nothing to the result", so libpam moves on to `pam_unix` or whatever
else the stack lists. It fails closed when nothing follows: a stack whose only
`auth` module returned `PAM_IGNORE` has no definitive result, and libpam answers
`PAM_PERM_DENIED`.

Check 3 has one subtlety that must survive the port: with `principals-map`
configured but unloadable, the module logs a **warning** and falls back to
requiring the certificate to carry the exact local account name. It does not
fail the login. A typo'd path degrades to the stricter default rather than
locking every account out of the host.

## Parsing the certificate

Check 1 needs the exact bytes the CA signed. The Go implementation reconstructs
them by copying the certificate, clearing `Signature`, re-marshaling, and
trimming the trailing four-byte length prefix that `Marshal` appends. A C parser
gets this for free and more safely: it walks the blob once and records the offset
where the `signature` field begins.

## Dependency decisions

These are the hard-to-reverse bets. Each is settled below with its rationale;
what remains genuinely open is in Open Questions at the bottom.

<Callout id="dec-curl" tone="decision">

**HTTP and TLS: libcurl.** The events endpoint is a long-lived streaming GET
that must stay open until a human acts, and the create call needs
proxy-from-environment, HTTP/2, and TLS 1.3 pinning — all of which the Go client
gets from `net/http` today. libcurl supplies them and is already resident on
every distribution that ships `sudo`. Hand-rolling HTTP over an OpenSSL `BIO`
would mean roughly 800 lines of chunked-encoding, redirect, and proxy handling
inside a root-privileged process, to save nothing: the shared library is on the
box either way.

Non-negotiable settings: `CURLOPT_NOSIGNAL = 1L` (libcurl otherwise uses
`SIGALRM` and `siglongjmp` for the synchronous resolver, which would corrupt
`sudo`'s signal state), `CURLOPT_FOLLOWLOCATION` left off (an auth flow must not
silently follow a redirect to another origin), and `CURLOPT_SSLVERSION =
CURL_SSLVERSION_TLSv1_3` to match the Go client's `MinVersion`. `curl_global_init`
runs under `pthread_once`; **`curl_global_cleanup` is never called**, because it
would tear down global state the host process may itself be using.

</Callout>

<Callout id="dec-openssl" tone="decision">

**Crypto: each platform's own system library, behind one internal interface.**
OpenSSL 3 on Linux and FreeBSD; Security.framework and CommonCrypto on macOS.
Every link-time dependency is something the operating system already ships —
there is no third-party library to install, vendor, or track CVEs for.

`src/crypto.h` defines the seam: generate a P-384 keypair, export its public
point, verify a signature given an algorithm name and an SSH-format public key,
hash, and wipe. `crypto_openssl.c` and `crypto_darwin.c` implement it. Everything
above that line — the wire reader, the certificate parser, the four checks — is
identical on every platform.

Neither libssh nor libssh2 is used. libssh2 has no certificate support at all,
and libssh is a full client stack whose certificate handling is not exposed as a
parsing API. The SSH wire format is length-delimited and simple enough that a
bounds-checked reader is smaller and easier to audit than either.

Signature verification must cover whatever key type an operator put in
`trusted-ca-file`: `ssh-ed25519` (raw 64-byte signature, one-shot verify),
`ecdsa-sha2-nistp{256,384,521}` (SSH packs `r` and `s` as separate mpints;
convert to a DER `ECDSA_SIG` and match the digest to the curve), and
`rsa-sha2-256` / `rsa-sha2-512` (PKCS#1 v1.5).

**`ssh-rsa` is rejected.** That algorithm name means RSA with SHA-1, which
OpenSSH has disabled by default since 8.8. `x/crypto/ssh` still verifies it, so
the Go module accepts an `ssh-rsa` CA today; the C module refuses it with an
explicit error naming the algorithm, rather than failing with a vague "not
signed by a trusted CA".

No current deployment signs with `ssh-rsa`, so this costs nothing at rollout —
there is no CA rotation to sequence ahead of it. The explicit error message
still earns its place: it is what a future operator gets if someone stands up a
CA with the wrong key type.

</Callout>

<Callout id="dec-json" tone="decision">

**JSON: vendored jsmn, pinned and checked in.** Exactly three response shapes
matter — the create response, the terminal-event envelope, and the error body —
and jsmn is a non-allocating tokenizer with no heap graph to corrupt. Responses
are capped at 64 KiB first, matching the Go client's own error-body cap. cJSON
is the fallback if walking tokens by hand turns out to be unwieldy in
`json.c`; a system `libjansson` dependency is rejected because it drags a
run-time dependency into a module that must load on minimal images.

Vendoring is not the same as linking, and the distinction is deliberate: jsmn is
a few hundred lines compiled into the module and auditable in an afternoon,
adding nothing to `ldd` output. The rule this plan holds to is that every
*link-time* dependency is an OS-provided library.

</Callout>

<Callout id="dec-syslog" tone="decision">

**Logging: `syslog(3)` with no `openlog` / `closelog`.** `openlog` mutates
process-global state (ident, facility, options) and `closelog` closes a
descriptor the host may be holding. Inside `sudo` that is not ours to touch. The
module calls `syslog(LOG_AUTHPRIV | LOG_INFO, ...)` directly and puts
`pam_ssoossh:` at the front of every message, so log lines stay greppable
without the module reconfiguring the host's logging.

The version line stays unconditional at `LOG_INFO` on every invocation — a
module that only reports its version when `debug` is already enabled is a worse
support problem than one extra line per `sudo`.

**That line now carries the linked library versions too**, from
`OpenSSL_version(OPENSSL_VERSION)` and `curl_version()`:

```
pam_ssoossh: 1.0.0 (a1b2c3d, 2026-09-04) | OpenSSL 1.1.1k  FIPS 25 Mar 2021 | libcurl/7.61.1
```

The module links crypto rather than shipping it, so which crypto is actually
resident in `sudo` is a property of the host, not of our release. One extra
field makes that answerable across a fleet by grepping syslog — including
the case that matters, a host still running an OpenSSL its distribution stopped
patching. On macOS the same field reports the Security.framework backend, which
has no version to print, so it names the backend instead.

</Callout>

<Callout id="dec-cancel" tone="decision">

**Timeouts: a monotonic deadline on a `curl_multi` poll loop.**
`clock_gettime(CLOCK_MONOTONIC)` at entry, `curl_multi_poll` with the remaining
milliseconds each tick, and the transfer torn down on expiry. This reproduces
the `timeout` argument without any of Go's `context` machinery.

</Callout>

<Callout id="dec-sigint" tone="decision">

**Ctrl-C hands the stack to the next module, it does not abandon `sudo`.**
Waiting on a browser is a long block with a human in front of it, and someone
who gives up on it usually wants the password prompt that `pam_unix` would have
given them — not a dead `sudo`. So the module does install one handler, but a
deliberately narrow one:

`sigaction(SIGINT)` is installed immediately before the wait and the previous
disposition restored immediately after, on every exit path. The handler does
nothing but set a `volatile sig_atomic_t` flag; the `curl_multi_poll` loop
notices it on the next tick, tears the transfer down, and returns
**`PAM_IGNORE`**, which tells libpam to skip this module and continue.

SIGTERM gets no handler at all — that signal means someone is killing the
process, and swallowing it inside a PAM module would be a bug. And because the
old handler is back in place before the module returns, a second Ctrl-C behaves
exactly as it would have without this module loaded.

</Callout>

<Callout id="dec-control-flag" tone="decision">

**`sufficient` is the documented stanza, and the only one.** An approval ends
the auth stack; anything else — a cancellation, a denial, a timeout, an
unreachable server — hands over to whatever comes next, normally `pam_unix`.

That means **a denied approval falls through to the password prompt**, which
`requisite` would have made final. It is the intended posture rather than a side
effect: ssoossh is an additional way to authenticate, not a gate that can lock
an operator out of a host when the browser flow is unavailable. The browser
approval is what lets someone `sudo` *without* their password; being refused
there returns them to the password they already had.

A stricter posture is expressible — Linux-PAM's bracketed actions, OpenPAM's
`binding` — but publishing two stanzas invites a deployment to pick the wrong
one, so the documentation offers a single stanza and this plan records why.

</Callout>

<Callout id="risk-ignore-semantics" tone="risk">

`PAM_IGNORE` dropping through to the next module is the load-bearing assumption
in the cancellation design, and it is worth proving rather than reading. P1
verifies it empirically — a two-module stack, `pam_ssoossh` then `pam_unix`,
Ctrl-C at the approval prompt, confirming the password prompt appears — against
Linux-PAM and OpenPAM separately, since the two dispatchers are independent
implementations, and against every control flag the documentation recommends
(`sufficient`, the bracketed form, and `binding`). A dispatcher that treats
`PAM_IGNORE` as a failure under one of those flags is a documentation bug, not a
module bug, but it has to be found before the stanza is published.

</Callout>

## Platforms and packaging

<Callout id="dec-standalone" tone="decision">

**This is a standalone repository with its own release cadence.** The version
string is `git describe` at build time, baked in with `-DPAM_SSOOSSH_VERSION=`,
replacing the `internal/version` values goreleaser injects today. The module
keeps logging that version unconditionally at `LOG_INFO` on every invocation.
The monorepo's `pam_ssoossh/` directory is removed once the C module has shipped
and the differential harness has run clean for a release; until then both exist
and the harness runs in CI.

</Callout>

Three PAM implementations across four targets is not one build with four
triples — OpenPAM is a different library with a different dispatcher, and macOS
is a different linker. The Makefile branches on `uname -s`.

<Callout id="dec-macos" tone="decision">

**macOS is a developer and CI target, not a shipped artifact.** It exists to
keep the OpenPAM paths — the return-code constants, the `ld64` symbol list, the
`PAM_IGNORE` dispatch — under test on every commit. FreeBSD is the OpenPAM
target that actually ships. That keeps SIP and installer questions out of the
project entirely: nothing has to land in `/usr/lib/pam/`.

Baseline is **macOS 15 Sequoia**, arm64, built with
`-mmacosx-version-min=15.0` on GitHub's `macos-15` runners. For local testing,
`/etc/pam.d/` entries accept an absolute module path, so a build can be
exercised straight out of the build directory without touching a
SIP-protected location:

`auth sufficient /Users/you/ssoossh-pam-c/pam_ssoossh.so server=...`

</Callout>

<Callout id="dec-macos-ssl" tone="decision">

**macOS uses Security.framework and CommonCrypto, not OpenSSL.** System SSL is
not an option there: macOS ships LibreSSL as a dylib, but the SDK exposes no
`openssl/*.h` and no linkable stub, and Apple does not support third-party
linking against it. That leaves Homebrew `openssl@3` or Apple's own APIs, and
Apple's own APIs win — a module that links only what the OS ships has no
install-time dependency, no second copy of a TLS stack in a root process, and no
third-party CVE surface to track.

`SecKey` covers P-384 generation, ECDSA verification, and RSA PKCS#1 v1.5 with
SHA-256 and SHA-512. It does **not** cover Ed25519: Apple's Ed25519 is in
CryptoKit, which is Swift-only with no C API. So macOS supports every CA key
type this module accepts except `ssh-ed25519`, and that limit is documented
rather than worked around. The capability matrix below is the definition.

libcurl needs no equivalent decision — macOS ships it with SDK headers and a
linkable stub, so it is a system library there like everywhere else.

</Callout>

The ephemeral keypair the module generates per attempt is always ECDSA P-384,
which every backend supports, so this table only ever constrains the *CA* side.

<Callout id="dec-ca-skip" tone="decision">

**An unsupported CA key is skipped with a warning, not a fatal error** — unless
it was the only one. `trusted-ca-file` holds one key per line specifically so a
deployment can rotate CAs without a coordinated restart, and a file mid-rotation
may legitimately list a key this platform cannot use. Each unusable key is
logged at warning level naming the algorithm and the line, and loading continues.
If no usable key remains, that is `PAM_NO_MODULE_DATA` with an error saying so —
the same code an empty or unreadable file produces.

The failure mode this avoids: an Ed25519 CA appended to the file on a Friday
takes every macOS host offline, and the log says "not signed by a trusted CA".

</Callout>

<Callout id="dec-version-floor" tone="decision">

**RHEL 8 sets the floor: OpenSSL 1.1.1 and libcurl 7.61.** RHEL 8 is in
Maintenance Support until 31 May 2029, a longer runway than any other old
target, so it — not Amazon Linux 2 — is the constraint worth designing to.
Amazon Linux 2 comes along at no extra cost provided `openssl11` is installed.

**This is a project boundary, not an observation about what happens to be
deployed.** OpenSSL 1.0.2 and the releases that carry it — RHEL 7, CentOS 7 —
are out of scope permanently. That is where `EVP_MD_CTX` and the `ECDSA_SIG`
accessors become structurally different rather than renamed, which would mean a
third API path through the file that verifies certificates as root, to serve a
crypto library upstream stopped patching in 2019. A build against anything older
than 1.1.1 fails at compile time rather than producing a module nobody intended:

```c
#if OPENSSL_VERSION_NUMBER < 0x10101000L
#  error "pam_ssoossh requires OpenSSL 1.1.1 or newer (RHEL 8 baseline)"
#endif
```

A host that old still has a route — an `OPENSSL_PREFIX` build against a
self-maintained OpenSSL, below — but it is that host's problem to solve, not a
shape this source carries.

Depending on system libraries makes the oldest supported distribution a real
constraint in a way it never was for the Go build, which statically links its
own crypto and only ever paid for old glibc symbol versions. Two concrete costs:

- **`curl_multi_wait` instead of `curl_multi_poll`** (the latter is 7.66+). The
  deadline loop passes `min(remaining, curl_multi_timeout())` and sleeps ~100 ms
  itself when `numfds == 0`, which is the documented way around
  `curl_multi_wait` returning immediately when there is no descriptor to wait on
  — briefly the case during name resolution.
- **Constructing an `EVP_PKEY` from raw components.** Key *generation* needs no
  guard at all: the `EVP_PKEY_CTX_new_id` / `set_ec_paramgen_curve_nid` path
  works unchanged on 1.1.1 and 3.0. The guards are confined to three small
  functions that build a public key from SSH wire components —
  `EC_KEY_oct2point` + `EVP_PKEY_assign_EC_KEY` and `RSA_set0_key` on 1.1.1,
  `EVP_PKEY_fromdata` on 3.0. Ed25519 needs none: `EVP_PKEY_new_raw_public_key`
  has been there since 1.1.1.

The guards decide which API a given build calls, not which OpenSSL a host runs.
A Debian 12, RHEL 9, or FreeBSD 14 build compiles the 3.0 path and links its own
system OpenSSL 3; supporting the older floor drags no modern host onto older
code.

**The guards have no retirement date.** They come out when there is evidence no
RHEL 8 host is left, and the deployment reality this is built for — hosts kept
running past their distribution's end of life as a matter of course — means that
is expected to be a long way off, past May 2029 rather than before it. The
version line in syslog is what will eventually make "no RHEL 8 left" a
statement of fact rather than a hope. The guards are narrow enough that
carrying them indefinitely is not a burden worth optimizing away.

</Callout>

<Callout id="dec-alt-openssl" tone="decision">

**The Makefile accepts an alternate OpenSSL prefix**, so a host on a
distribution that has stopped issuing OpenSSL updates can still be given patched
crypto without touching module source:

```
make OPENSSL_PREFIX=/opt/openssl-3.5
```

which prepends that prefix to `PKG_CONFIG_PATH` and sets an `RPATH` on the
module. This exists because running past end of life is planned for here, and
the alternative when a CVE lands on a frozen distribution package is having no
move at all.

It has a sharp edge when the private OpenSSL is loaded as a shared object.
libcurl in the same process links its own libcrypto, so this can put two
OpenSSLs in one `sudo`. Crossing a major version is the safe case —
`libcrypto.so.1.1` and `libcrypto.so.3` have different SONAMEs and are designed
to coexist. A *same-SONAME* replacement, such as a private 3.5 on a host whose
system OpenSSL is also 3.x, is the dangerous one.

</Callout>

<Callout id="dec-bundled-builds" tone="decision">

**Bundled-crypto builds are published alongside the normal ones**, so a host on
a distribution that has stopped issuing OpenSSL updates has an artifact to
install rather than a build to perform during an incident.

The published variant links libcrypto **statically**, not as a private shared
object, which removes the SONAME hazard entirely rather than documenting around
it. The module already builds with `-fvisibility=hidden` behind a version script
exporting only `pam_sm_authenticate` and `pam_sm_setcred`, so a statically
linked libcrypto is invisible to the rest of the process: no SONAME to collide,
nothing exported to interpose. libcurl continues to use the system libcrypto for
TLS, and the two copies never exchange objects — the module hands libcurl URLs
and reads bytes back, never an `EVP_PKEY`. OpenSSL 1.1.1 and later self-initialize
and need no locking callbacks, which is what makes two in-process copies
tractable at all.

The size target for this variant is separate and much larger — roughly 1.5–2.5 MB
against the 512 KB of a normal build — and that is fine. It is still several
times smaller than the 12.9 MB it replaces, and it is the variant chosen
deliberately by an operator who has decided a bundled OpenSSL is the lesser
problem.

**Scope: Linux glibc, x86-64 and arm64, and nothing else.** That is where the
RHEL 8 and past-end-of-life hosts this variant exists for actually are. Alpine
tracks OpenSSL closely enough that a musl bundle would mostly duplicate what the
distribution already does well; FreeBSD carries OpenSSL in base and moves it with
the release; macOS has no OpenSSL in the picture at all and ships no artifact.
Narrowing to one platform also keeps the patching obligation below to a single
build matrix.

**Pin: the current OpenSSL LTS — 3.5 at the time of writing — rebuilt
best-effort on High or Critical advisories.** Best-effort is the honest word and
it belongs in the release notes rather than only here: this is a personal
project deployed at work, not a vendor with a pager rotation, and an operator
choosing a bundled artifact should know they are choosing that cadence. Low and
Moderate advisories ride along with the next release rather than triggering one.

</Callout>

<Callout id="risk-bundled-obligation" tone="risk">

**Publishing bundled builds is a standing obligation, and it should be written
down as one.** Everywhere else this plan pushes crypto maintenance onto the
distribution; this variant takes some of it back. Concretely, the project now
owns: pinning an OpenSSL version for bundled artifacts, watching OpenSSL
advisories against that pin, and cutting a module release whenever it moves —
including releases where nothing in this repository's own source changed.

Two failure modes worth naming. A bundled artifact that lags upstream is *worse*
than the system OpenSSL it was meant to improve on, and nothing in the module
will say so — which is exactly why the syslog version line reports the linked
OpenSSL for these builds too, making a stale bundle visible in the same way an
unpatched system one is. And an operator who installs a bundled build to dodge a
CVE and then never updates it has swapped a vendor's patch cadence for ours; the
release notes for these artifacts should say that plainly.

What makes this survivable is that it is one build matrix on one platform against
one pinned LTS line, and that the commitment is stated as best-effort rather
than implied to be more. The moment it grows a second platform or an implied
turnaround, it stops being a side artifact and becomes release engineering.

</Callout>

<Callout id="risk-macos-sdk" tone="risk">

The SDK specifics above are the reason macOS is CI-only rather than a shipping
target, so P0 confirms them against the actual Sequoia SDK before the platform
matrix is treated as settled: that `$(xcrun --show-sdk-path)/usr/include` has
curl headers but no `openssl/`, and that `-exported_symbols_list` hides the
vendored jsmn symbols as effectively as the ELF version script does.

</Callout>

## Console mode

`docs/proposals/console-login-pam.md` in the monorepo designs a second flow:
a console with no browser and no copy/paste displays a short code and a QR
code, and the approver types the code into the web UI. It is marked
*researched, nothing built*, and it depends on server work — a new `console`
certificate type, two migrations, `POST /api/certs/console`, a code-resolution
endpoint, and two frontend routes — none of which lives in this repository.

This plan does not adopt that scope. It adopts the proposal's **module half**,
and treats the rest as a dependency that lands in the Go monorepo first. What
follows is what the C module has to become, and what P0–P6 must get right now so
console mode drops in later instead of forcing a rewrite.

<Callout id="dec-console-one-so" tone="decision">

**One shared object with a `mode` argument, as the proposal recommends — and
the argument is stronger in C.** `mode=sudo` is the default and is today's
behavior exactly; `mode=console` selects the other flow; an unrecognized value
fails with `PAM_NO_MODULE_DATA` rather than falling back, matching how a missing
`trusted-ca-file` already behaves.

The proposal's reasoning is that two modules would mean two copies of four
security checks that must stay in lockstep. In C there is more to keep in
lockstep: the crypto seam and both its backends, the bounds-checked wire reader,
and the certificate parser. Duplicating those across two `.so`s to save roughly
a hundred lines of difference would be the worst structural decision available.

**Console mode is compiled in on Linux and FreeBSD only.** macOS is a
developer and CI target for the `sudo` flow; a console login on a host nobody
ships to is scope with no user. `mode=console` on a Darwin build is rejected at
argument-parse time with the same fail-closed error an unrecognized mode gets,
and the QR encoder and console channel code are `#ifndef __APPLE__` so they are
not in that build at all.

</Callout>

<Callout id="dec-console-qr" tone="decision">

**QR rendering happens in the module, using a vendored encoder.** The proposal
weighs rendering server-side and shipping ANSI art in the create response, and
rejects it because that means writing server-supplied bytes to a terminal. That
reasoning is right and this plan follows it.

The encoder is Nayuki's `qrcodegen` — MIT, one `.c` and one `.h`, no allocation
when the caller supplies buffers — vendored and pinned beside jsmn. It adds no
link-time dependency, which is the rule this plan holds to everywhere else.
Version 3 at error-correction level L encodes the ~40-character complete
verification URL in 29×29 modules; drawn two QR rows per terminal row with
half-block characters and a 2-module quiet zone, that is 33 columns by 17 rows,
which fits an 80×24 console with the surrounding text.

</Callout>

<Callout id="risk-tty-injection" tone="risk">

**Everything the module writes to the conversation gets whitelisted first, and
this is a fix the `sudo` flow needs today.** The current Go module passes the
server's approval URL straight into `PAM_TEXT_INFO`:
`conv.Info(fmt.Sprintf("Approve this request in your browser:\\n%s", pending.ApprovalURL))`,
where `ApprovalURL` is a field from a JSON response. A compromised or spoofed
`ssoosshd` — or any server reached with `insecure-skip-verify` — can therefore
put arbitrary bytes, including terminal escape sequences, on the tty of a
process running as root.

The C module filters every byte before it reaches the conversation, in one
function, for both modes: the code against Crockford Base32 plus the group
separator, the URL against an unreserved-URL character set, and the QR against
exactly `U+2580`, `U+2584`, `U+2588`, space, and newline. Anything else is
dropped and the rejection logged. This lands in **P1** with the conversation
code, not in the console phase, because the exposure exists in the flow that
ships first.

</Callout>

Beyond arguments, four things change inside the module. The conversation seam
grows a second operation, since `prompt=enter` needs `PAM_PROMPT_ECHO_ON` and
its response string has to be freed by us. Request context — `PAM_SERVICE`,
`PAM_TTY`, `PAM_RHOST` via `pam_get_item`, plus the hostname — is read and sent
so the approver can tell a real console login from one an attacker started. The
create call becomes endpoint-parameterized rather than hardcoded to
`/api/certs/pam`. And the wait is bounded by `min(timeout, expires_at)` using
the server's own expiry rather than a local guess.

<Callout id="dec-expires-at" tone="decision">

**`expires_at` is honored in P4, before console mode needs it.** The proposal
adds it to every create response, not just console ones, and it fixes a real
defect in the `sudo` flow as it stands: the module's `timeout` and the server's
`client_timeout` are two numbers an operator has to keep in agreement by hand,
and getting it wrong leaves the module waiting on a request the server already
killed, reported as a generic timeout.

Honoring it costs an RFC 3339 parse and a `min()`. jsmn ignores fields it was
not asked for, so a server that does not send it yet degrades to today's
behavior with no version negotiation.

</Callout>

## Risks and sharp edges

<Callout id="risk-parser" tone="risk">

**A parser running as root on bytes a network peer chose.** This is the whole
security weight of the project. Mitigations, all in place before P4 connects
anything real: every field read through `sshwire.c`, no pointer arithmetic
outside it; hard caps before parsing (certificate ≤ 32 KiB, HTTP response ≤ 64
KiB, SSE line ≤ 1 MiB to match the Go client); `-fsanitize=address,undefined` on
the whole unit suite; libFuzzer corpora seeded from real ssoosshd output. A
`trusted-ca-file` is operator-controlled and gets the same treatment anyway.

</Callout>

<Callout id="risk-symbols" tone="risk">

**Symbol collision inside the host.** A PAM module is `dlopen`ed into a process
with its own symbol table. Vendored jsmn symbols, or a helper named `parse`,
leaking into `sudo` is a real failure mode. `-fvisibility=hidden` plus the
version script is the fix; `nm -D --defined-only` in CI is the check that it
stays fixed.

</Callout>

<Callout id="risk-stdio" tone="risk">

**Nothing may write to stdout or stderr.** The module lives inside `sudo` and
`sshd`, where both streams belong to the host. The Go project enforces this as a
written rule; the C port gets a CI grep for `printf|fprintf|puts|perror|write\\s*\\(\\s*[12]`
outside `tests/`. Dropping `debug=stdout` removes the only path that ever
deliberately broke the rule, so the grep can be an unconditional failure rather
than one with an exemption in it.

</Callout>

<Callout id="risk-drift" tone="risk">

**Silent behavioral drift.** Two implementations of the same protocol diverge in
the cases nobody tests. The countermeasure is the differential harness in P6:
both modules, the same `pam.d` stanza, the same stub server, the same scenario
list, comparing PAM return code and the decision line in syslog. Any divergence
is a bug in the C module until proven otherwise, with Ctrl-C the one sanctioned
exception.

The harness runs on Linux only, and that is a real limit rather than an
oversight. The Go module hardcodes Linux-PAM's numeric return codes, so on
FreeBSD or macOS it is not a correct reference to compare against — it would
report `PAM_PERM_DENIED` where it means `PAM_AUTH_ERR`. OpenPAM correctness is
established by the platform's own test runs and the `PAM_IGNORE` fallthrough
check, not by differencing against a module that was never right there.

</Callout>

<Callout id="risk-patch-boundary" tone="risk">

**We link crypto; we do not ship it or patch it.** That boundary should be
stated once, plainly, because the version numbers invite the wrong conclusion.
A RHEL 8 host reports `openssl-1.1.1k`, but that is a Red Hat package carrying
years of backported fixes under a frozen version string — not upstream 1.1.1k
from March 2021. Upstream 1.1.1 has been end-of-life since 11 September 2023;
the patch stream that matters is the distribution's, and `rpm -q --changelog
openssl` is where it is legible.

Two layers of OpenSSL sit in the host process, and only one of them is ours.
Directly, `libcrypto` does key generation, signature verification, and hashing
over inputs the module has already bounds-checked itself. Indirectly, libcurl
drives `libssl` for TLS, including X.509 chain parsing of whatever certificate
`ssoosshd` presents — historically the larger surface, and the one that
CVE-2022-0778's certificate-parsing infinite loop is the archetype of. That
second layer is present for anything using system libcurl and is not a cost this
port introduces.

While a distribution is still issuing updates this is an improvement over the
status quo. The Go module statically links Go's own TLS and crypto, so an
advisory there needs a rebuild and a fleet-wide redeploy of `pam_ssoossh.so`;
the C module is fixed by the `yum update openssl` the operations team already
runs. On RHEL the same choice also improves the FIPS story, since system OpenSSL
in FIPS mode is the supported route to validated crypto.

**That advantage is conditional on the distribution still publishing fixes, and
here it often will not be.** Hosts are expected to run past end of life as
normal practice in the environment this targets, and a frozen package on an
unsupported release receives nothing. Past that point the comparison inverts:
the Go module carries crypto that a rebuild can update, while this one links
crypto that nobody is updating. Two things answer that, and both are decided
above rather than left implicit — the linked versions are logged at `LOG_INFO`
so an unpatched host is findable rather than assumed, and `OPENSSL_PREFIX` lets
a host be given patched crypto without a source change when a CVE lands on a
package its vendor will not fix.

The default artifact keeps the narrow version of that promise: it must never be
the reason someone cannot apply a fix. It bundles no crypto, pins no private
copy, and needs no module release to pick up a system one.

The bundled-crypto variant is the deliberate exception, and it inverts the
responsibility rather than sharing it — for those artifacts, OpenSSL patching is
this project's job. That is a real obligation and it is stated as one below,
not buried as a build flag.

</Callout>

<Callout id="risk-secrets" tone="warning">

**The private key exists in a root process's heap.** It is per-attempt and never
written anywhere, but it must be wiped rather than merely freed:
`OPENSSL_cleanse` the key material and `EVP_PKEY_free` on every exit path,
including the error paths. A `goto cleanup` discipline in `auth.c` rather than
early returns.

</Callout>

Three of these reshaped the plan rather than settling a toggle.

Falling through to `pam_unix` on Ctrl-C is not the same requirement as "do not
install handlers" — it needs the module to *notice* the signal, which is why the
design is a narrow save/restore handler returning `PAM_IGNORE` rather than no
handler at all. It makes the C module behave better than the Go one here, since
`PAM_AUTH_ERR` kills the whole `sudo` attempt today.

`sufficient` as the sole stanza settles a policy, not a syntax: ssoossh is an
additional way to authenticate rather than a gate, so a refusal in the browser
returns the operator to the password they already had. The strictness that
`requisite` provided is gone deliberately, and the plan says so where an
implementer will read it.

Holding the line on link-time dependencies is what produced the crypto seam.
Rather than one crypto library everywhere, `src/crypto.h` fronts OpenSSL on
Linux and FreeBSD and Apple's own APIs on macOS, so no platform needs anything
the OS does not already ship. The cost is one capability gap — no `ssh-ed25519`
CA on macOS — and that gap is defined in the capability matrix, asserted by a
test, and reported at runtime as an error naming the algorithm. A vendored
Ed25519 verifier would close it without adding a linked dependency, and remains
available if the limit ever becomes real for a deployment; it is not worth
carrying extra crypto code in a root process on the chance.
